## 1. The question

A data availability statement naming an OSF project is treated, by every study that grades
statements including this project's own, as evidence that data are available. That inference
has a missing step. The statement is a promise; whether the promise was kept is a separate fact
and it is checkable.

## 2. Hypothesis

A material fraction of statements graded `actionable` do not resolve, and the fraction rises
with the age of the article.

**Primary null.** The proportion of non-resolving locators does not vary with article age.

**What would falsify the hypothesis.** A flat or declining relationship with age. A high but
age-invariant failure rate would mean statements are wrong on arrival rather than decaying,
which is a different problem and a more serious one.

## 3. Design

Cross-sectional study of locators, with a nested age analysis.

## 4. Sample

Every statement extracted by P01 and P01v2 that carries at least one locator. Probe PA:

| quantity | value |
|---|---|
| statements examined | 2262 |
| statements carrying a locator | 431 |
| locators found | 721 |
| of which URLs | 644 |
| of which bare DOIs | 77 |
| on a known repository host | 504 |

The three hosts that dominate are OSF, GitHub and doi.org. That concentration is itself a
finding and it constrains the design: a result here is substantially a result about three
services, and section 8 carries that.

## 5. Measurement

HEAD first, falling back to a ranged GET when a host answers 403, 405 or 501, since several
repositories refuse HEAD but serve GET. One request per locator, throttled per host, with a
User-Agent naming the project and a contact address. This is a read-only availability check of
the kind these hosts exist to serve.

**Resolution is not the same as the data being there.** A repository landing page for a project
with no files attached returns 200. The primary outcome is therefore HTTP resolution, which is
a lower bound on breakage, and a hand-checked subsample of 100 resolving locators establishes
how often a 200 corresponds to retrievable data. That subsample needs the author.

## 6. Feasibility, computed

On a sample of 150 locators, one per article:

| outcome | n |
|---|---|
| resolved, HTTP 2xx or 3xx | 133 |
| HTTP error | 9 |
| network or requester error | 8 |
| **resolve rate** | **88.7 percent** |

7 hard 404s in 150 is the cleanest signal: those
are locators that a reader following the statement would not find. The study is feasible and
the effect is large enough to measure.

## 7. Outcome and analysis

**Primary**: locator resolves, yes or no.

In R, logistic regression of resolution on article age, with host as a random intercept because
three hosts carry most of the sample and their reliability differs.

```r
glmer(resolved ~ years_since_pub + kind + (1 | host), family = binomial, data = d)
```

Preregistered sensitivity analyses:

1. Restricted to repository hosts, excluding personal and institutional URLs.
2. Excluding doi.org, which resolves through a redirection layer that may mask a dead target.
3. Treating a 403 as resolved rather than failed, since a paywall is not link rot.
4. Re-running every failure once, at least 48 hours later, so a transient outage is not
   recorded as permanent breakage.

You are a hypothesis-driven debugger. Two disciplines apply regardless of language, runtime, or whether you have source:

1. **Runtime truth beats code reading.** Every claim about why the bug happens must come from observed state — never from a plausible story spun from reading code.

## 1. The question

A data availability statement naming an OSF project is treated, by every study that grades
statements including this project's own, as evidence that data are available. That inference
has a missing step. The statement is a promise; whether the promise was kept is a separate fact
and it is checkable.

## 2. Hypothesis

A material fraction of statements graded `actionable` do not resolve, and the fraction rises
with the age of the article.

**Primary null.** The proportion of non-resolving locators does not vary with article age.

**What would falsify the hypothesis.** A flat or declining relationship with age. A high but
age-invariant failure rate would mean statements are wrong on arrival rather than decaying,
which is a different problem and a more serious one.

## 3. Design

Cross-sectional study of locators, with a nested age analysis.

## 4. Sample

Every statement extracted by P01 and P01v2 that carries at least one locator. Probe PA:

| quantity | value |
|---|---|
| statements examined | 2262 |
| statements carrying a locator | 431 |
| locators found | 721 |
| of which URLs | 644 |
| of which bare DOIs | 77 |
| on a known repository host | 504 |

The three hosts that dominate are OSF, GitHub and doi.org. That concentration is itself a
finding and it constrains the design: a result here is substantially a result about three
services, and section 8 carries that.

## 5. Measurement

HEAD first, falling back to a ranged GET when a host answers 403, 405 or 501, since several
repositories refuse HEAD but serve GET. One request per locator, throttled per host, with a
User-Agent naming the project and a contact address. This is a read-only availability check of
the kind these hosts exist to serve.

**Resolution is not the same as the data being there.** A repository landing page for a project
with no files attached returns 200. The primary outcome is therefore HTTP resolution, which is
a lower bound on breakage, and a hand-checked subsample of 100 resolving locators establishes
how often a 200 corresponds to retrievable data. That subsample needs the author.

## 6. Feasibility, computed

On a sample of 150 locators, one per article:

| outcome | n |
|---|---|
| resolved, HTTP 2xx or 3xx | 133 |
| HTTP error | 9 |
| network or requester error | 8 |
| **resolve rate** | **88.7 percent** |

Status detail: `{'200': 123, '202': 10, '404': 7, 'error:UnicodeEncodeError': 2, '403': 2, 'error:TimeoutError': 3, 'error:URLError': 3}`

7 hard 404s in 150 is the cleanest signal: those
are locators that a reader following the statement would not find. The study is feasible and
the effect is large enough to measure.

## 7. Outcome and analysis

**Primary**: locator resolves, yes or no.

In R, logistic regression of resolution on article age, with host as a random intercept because
three hosts carry most of the sample and their reliability differs.

```r
glmer(resolved ~ years_since_pub + kind + (1 | host), family = binomial, data = d)
```

Preregistered sensitivity analyses:

1. Restricted to repository hosts, excluding personal and institutional URLs.
2. Excluding doi.org, which resolves through a redirection layer that may mask a dead target.
3. Treating a 403 as resolved rather than failed, since a paywall is not link rot.
4. Re-running every failure once, at least 48 hours later, so a transient outage is not
   recorded as permanent breakage.

It is recorded here rather than quietly fixed because the same class of error, a tool failure
scored as a property of the world, is exactly what this study is about.

## Things that are true and easy to get wrong

- **A large hit count is not automatically a broken query.** `"trial registration"` returns
  156828 PubMed records, and the obvious diagnosis, that PubMed broke the phrase into words and
  ANDed them, was wrong: the quoted form returns fewer records than `trial AND registration`, so
  it is phrase-indexed. The real cause is that **Trial registration** is a structured abstract
  section label carried verbatim by every registered trial. Test the two forms against each
  other before concluding anything about a phrase.
- **Run `--counts` before harvesting anything.** It costs a few minutes and it is what exposed
  the above. A block sized after it has been downloaded is a block downloaded twice.
- **A tier B topic phrase retrieves studies that did the thing, not studies about it.** No
  boolean query separates them. That is a classification problem for a later stage, not a query
  to be tuned.
- **NCBI returns at most 9999 ids per query.** `collect_ids` bisects the publication-date range
  recursively until every part is under the ceiling, and records any single day still over it in
  `gaps` rather than truncating silently. The sibling project stops at month granularity and can
  truncate without saying so; do not copy that behavior back.
- **The efetch cache is keyed on the content of each batch, not its position.** Position keying
  is wrong the moment a query changes, and the failure is silent because every printed count
  comes from esearch and stays correct while the parsed records go stale.

# Detectable p1 at 80 percent power with unequal allocation. power.prop.test assumes equal
# group sizes and would understate what 520 against 3435 can do, so the two-proportion normal
# approximation is solved directly for p1.
detectable_p1 <- function(n1, n0, p0, power = 0.8, alpha = 0.05) {
  za <- qnorm(1 - alpha / 2); zb <- qnorm(power)
  f <- function(p1) {
    pbar <- (p1 * n1 + p0 * n0) / (n1 + n0)
    num <- abs(p1 - p0) - za * sqrt(pbar * (1 - pbar) * (1 / n1 + 1 / n0))
    den <- sqrt(p1 * (1 - p1) / n1 + p0 * (1 - p0) / n0)
    num / den - zb
  }
  uniroot(f, c(p0 + 1e-4, 0.999))$root
}

or_of <- function(p1, p0) (p1 / (1 - p1)) / (p0 / (1 - p0))
p1_det <- detectable_p1(n1, n0, p0)
